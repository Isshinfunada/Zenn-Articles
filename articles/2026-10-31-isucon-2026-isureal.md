## はじめに

船長（せんちょう）と申します。

2年ぶりに開催された ISUCON 2026 に、初めて出てきました。

実務でパフォーマンスチューニングをがっつりやった経験はありません。slow query を眺めて索引を足したことがある、くらいです。

それでも出ようと思ったのは、バックエンドの性能改善だけに集中できるコンテストって、なかなかないじゃないですか。しかも、同じ問題に強い人たちがどう取り組んだのか、終わったあとに全部読める。

自分が詰まったところを、みんなはどうやって越えていったのか。

それが知りたくて、まずは自分が詰まった記録を残しておこうと思って、この記事を書いています。

1人チームです。ただ、手はほぼ全部 AI エージェントです。自分はコマンドを打たない。見て、選んで、一言理由を言う。事前にそう決めて臨みました。

## 一応、準備はしていました

半年くらい前から、自分の仕事の文脈をまるごと AI に渡すための[バーチャルモノレポ](https://zenn.dev/paraponera/articles/2026-09-09-virtual-monorepo-ai-agent)を育てていて、ISUCON もその中の1コンテキストとして準備しました。

やったのは3つです。

過去問を3回、AWS に競技相当の環境を建てて解いた。ベンチの前後でアクセスログと slow query と CPU と pprof を採って、どこが遅いかをダッシュボードで見られるようにした。それと、当日の初動の順番と、守るもの（耐久性を落とす設定はしない、変更は1つずつ戻せる形で）を決めた。

練習で食らった失敗がそのまま型になりました。自動更新がスコアをぶらす。設定を一括で変えると何が効いたか分からない。ヒット率を確かめずにキャッシュを入れても効かない。

準備したぞ！という気持ちで当日を迎えました。

## 開始早々、ベンチまでたどり着けない

10時、競技開始。ポータルから CloudFormation のテンプレートを落として、環境を作ります。

ロールバックしました。

ルーター用のインスタンスが容量不足だそうです。いきなりかよ、と思いつつ、まあこれは自分のせいじゃないので、焦らず削除して作り直し。今度はちゃんと4台立ちました。

で、SSH が通らない。

4台全部通らない。

実はつい先日 1Password を導入したばかりで、SSH 鍵を脳死でポンポン放り込んでいたんですよね。事前に作って GitHub に登録したはずの鍵が、違う場所に入っていました。

・・・は？

結局、EC2 Instance Connect で root から入って、公開鍵を手で足して、isucon ユーザーに付け替えて、ようやく4台つながる。

最初のベンチが取れたのは 10:28。開始から30分溶けました。**4,253 点**。

これが初心者あるあるなのか、自分だけなのかは分かりません。ただ、練習では「環境を建てる」ところは Terraform で済んでいたので、当日の手順にこの時間を見込んでいなかったのは完全に自分の甘さでした。

## 直すと、次が詰まる

ここからは練習どおりです。自動更新を止めて、計測を仕込んで、計測ありの基準を取る。索引をまあまあ足す。これで **8,297**。倍になりました。この時点で「お、いけるじゃん」という気持ちになります。

今年の問題は ISUREAL。サーバーが4台で、asia に2台、europe と america に1台ずつ。地域間の遅延と帯域制限がルーターで再現されていて、DB は asia の1台を全地域で共有しています。欧米のユーザーは配点が 1.5 倍。

マニュアルを読みながら気になったのは2つでした。遠いリージョンのユーザーは、SQL を1本投げるたびに asia まで 100ms の往復を払う。これは何かしないとまずい。それと、画像がめちゃくちゃ多い。

なので、欧米のリクエストを asia のアプリに飛ばしてみます。

下がりました。

asia1 の CPU が張り付きました。

戻します。じゃあ CPU を減らそう、ということで pprof を見ると、画像の JPEG デコードと署名計算が CPU の大半。そこを削る。上がる。

今度は DB が張り付きます。

DB の待ちを分解して、ロックの持ち方を変えて、画像の格納方式を変えて、検索の SQL を作り直す。上がる。

するとまた asia1 の CPU が張り付きます。

**これを、くるくるくるくる、ずっと繰り返していました。**

![スコアの推移](/images/2026-10-31-isucon-2026-isureal/score-timeline.png)

どこかを速くすると次が詰まる。詰まったところを見に行くと、さっきまで見えなかったものが見える。これが全然飽きなくて、超面白かったです。

ちなみに途中で、「欧米からの往復が遅い」と思っていたものの正体が、往復そのものじゃなくて「往復しながらロックを握り続けていること」だった、という発見がありました。ロックを握っている側のトランザクションが、asia だと 146ms で閉じるのに、欧米だと 600ms 開きっぱなし。だから書き込みだけを asia のアプリに飛ばして、読み取りと画像は各地域で返す形にしました。これはかなり効きました。

## 当日の体制

ざっくり言うと、三体構成です。

- **手元のメインセッション（Opus）**: サーバーに入る、デプロイする、ベンチを回す、記録する。次に何をやるかの分析もここ
- **実装ワーカー**: 施策を1つずつコードにして、テストを通して返す
- **クラウドセッション（Opus と Fable）**: 現状分析と、施策を考える係

特に DB まわりが怪しいことが多かったので、メインセッションが psql で実際の DB の状態（遅いクエリ、ロック待ち、実行計画）を取ってきて、それをクラウド側の Fable に投げる、という動きをしていました。

自分は何をしていたかというと、ダッシュボードを見ています。

API ごとにどこが遅いか。各プロセスが CPU をどれだけ食っているか。遅いクエリ。関数ごとの時間。「この辺がまずいんだな」が分かるように練習のときから作ってきたやつです。

気になったところをクラウドセッションに聞く。施策をいくつか出してもらう。出てきたものには判断基準（根拠の数字、手間、戻しやすさ）がついているので、筋が良さそうなものを自分が選んで、反映してもらう。

正直、スコアが上がると楽しいので、どんどん出したくなります。

ただ、何回か止めました。「A〜F まとめて入れましょう」と来たときに、「先に DB が CPU で詰まってるのか、どのクエリが重いのか見せて」と言った場面が2回あって、どちらも次の一手が変わりました。

おかげで、今何をやっているのかに置いていかれずに改善を進められた感覚があります。これは地味に嬉しかった。

## 何を基準に選んでいたか

あとから振り返ると、だいたいこの順番でした。

1. 明らかにここ遅いね、というところ
2. 採点基準を見て、大事そうなところ・配点が高いところ
3. CPU が張り付いていたら、先にそのプロセスを分解して減らせるか頑張る
4. それで DB が張り付いたら、今度は DB を頑張る

3と4を往復しているだけとも言えます。でも、往復するたびに見えるものが変わるので、同じことをしている感じはしませんでした。

ちなみに、開始して早々に数十万点を叩き出している人がいました。

あ、これ今回は無理だな、と分かりました。

分かってからは自分のペースで行けたので、むしろよかったです。

## 残り2時間で、何も思いつかなくなった

16時くらいでした。

やれることは一通りやって、ダッシュボードを見ても「ここだ」というものがない。クラウドセッションに聞いても、出てくる案の見込みが小さい。

ここで一度、何を考えてきたかを振り返ってもらいました。そのときのメモが、この記事の元になっています。

で、振り返っていて思ったのが、後半ずっと「europe と america からのアクセスを、いかに asia の DB につながせないか」を考えていたんですよね。書き込みだけ飛ばす、接続数を絞る、欧米にキャッシュを置く。

でもこれ、**思い切って europe と america に DB を建てちゃえばよかったのかもしれない**。

読み取りレプリカを置いて、読み取りは地域内で完結させる。書き込み後の読み取り整合性をどう守るかとか、初期同期で 16GB 送れるのかとか、壁はいくつもあります。残り2時間で着手する勇気はありませんでした。

ここは、他の人がどうしたのかをいちばん読みたいところです。

## やったことをざっくり

具体的な施策は、たぶんみんな同じようなことをやっていると思うので、ざっくりだけ。

| テーマ | やったこと |
| --- | --- |
| 索引と接続 | 画像・友達関係・セッションの索引。DB 接続の再利用。欧米だけ接続上限を絞る |
| 地域の配置 | 書き込みだけ asia に飛ばす。asia の2台目にもアプリを置いて振り分ける |
| ロック | ユーザー行ロックの取り方を変える。トランザクションを短く |
| 画像 | ディスクにキャッシュして nginx から返す。JPEG はヘッダだけ読む。格納方式とパーティションを変える |
| 署名 | HMAC の計算を減らす |
| PostgreSQL の設定 | WAL・checkpoint・bgwriter。ベンチ直前に CHECKPOINT |

やめたものもあります。欧米リクエストの全転送（asia が詰まる）。投稿処理を DB 関数に集約（往復はもう速かったので効かない）。欧米に画像キャッシュ（同じ画像がほとんど再来しない）。

## 学んだこと

**事前の理解で通用したもの**

初動の順番。索引と N+1。「分散させると次が見えてくる」。変更は1つずつ戻せる形で。ヒット率を先に確かめる。再起動試験は終盤前に1回。

練習でやったことは、ちゃんと使えました。SSH で30分溶かしても、そこから先は型どおりに戻れた。

**初めて出会ったもの**

地域間の遅延は、往復の数じゃなくてロックの保持時間に効く。

PostgreSQL の引き出し。TOAST の格納方式、パーティションへの同時 INSERT の拡張ロック、チェックポイント直撃、prepared statement の汎用プランで索引が外れる、pg_trgm、advisory lock。練習は全部 MySQL だったので、ここは当日その場で覚えました。

計測スクリプトの有無で数千点動く。同じコードで計測なしで回したら 8,000 点くらい上がって、え、となりました。

**予想とずれたもの**

全転送で asia が先に詰まった。検索を SQL で絞ったら逆に遅かった。DB 関数は効かなかった。事前キャッシュで DB の時間は減ったのに点は下がった。

ずれたときに「なんで？」と見に行くのが、いちばん学びになった気がします。
