## はじめに

船長（せんちょう）と申します。

2年ぶりに開催された ISUCON 2026 に、初めて出てきました。

実務でパフォーマンスチューニングをやったことは、一切ありません。Datadog を眺めて、エラーが起きたら対応する。それくらいです。

それでも出ようと思ったのは、バックエンドの改善点をひたすら探して直す、というのが単純にめっちゃ面白そうだったから。

それと、同じ問題を解いた強い人たちが、終わったあとに体験談を出してくれる。それを全部読める。これがめっちゃいいなと思いました。

自分が詰まったところを、みんなはどうやって越えていったのか。それを知るには、まず自分がどこで何を考えていたかを残しておかないといけない。

なので、この記事はその記録です。

結果から書いておくと、最終スコアは **63,243 点**（順位は追記）でした。初めて出てみたぜ、という感じです。

## 準備したこと

1人チームです。手は AI エージェント。

ただ、AI に「とりあえず改善して」と任せるだけだと、何が起きているのか何も分からないんですよね。

だから、自分が分かるように、**一次情報の集め方と表示の仕方**を、当日までに間に合う範囲で準備しようと思いました。

やったのは3つです。

**過去問を3回、AWS に環境を建てて解いた。**

最初の2回（ISUCON9 と ISUCON10 の予選）は、AI に解いてもらいました。答えも全部見ながら、なるべく高い点数になるように。そこで得た知見を、改善パターンとしてまとめてもらいます。

3回目の private-isu は、自分で。育ってきたダッシュボードとパターン集を見ながら、本番さながらに一緒に解いてみました。

**ベンチの前後で一次情報を採って、見られるようにした。**

アクセスログ、slow query、各プロセスの CPU、pprof。これをベンチのたびに採って、「どの API が遅いか」「どのプロセスが CPU を食っているか」「どのクエリが重いか」「どの関数に時間がかかっているか」を前回との差分つきで見られるダッシュボードにしました。

![API ごとの回数・合計時間・p99・転送量。遅いものに「重」「注意」の札がつく](/images/2026-10-31-isucon-2026-isureal/dashboard-api-list.png)
*ベンチが終わると、API 一覧がこう出ます。この回は通知の SSE が 71% を占めていますが、接続しっぱなしなので遅さとは別です*

![判断材料。遅いクエリ、プロセスごとの CPU、関数ごとの時間、台ごとの CPU を一画面に](/images/2026-10-31-isucon-2026-isureal/dashboard-judgement.png)
*その下に「判断材料」。遅いクエリ、どの台のどのプロセスが CPU を食っているか、pprof で関数ごとの時間、台ごとの CPU。これを見て「次はここかな」を決めていました*

**当日の手順と、守るものを決めた。**

まず当日マニュアルを読む。これが一番大事、と事前に読んだ体験談のほとんどに書いてあったので。それから、つなぐ → 退避 → 素の基準 → 計測を仕込む → 施策、の順番。変更は1つずつ戻せる形で。耐久性を落とす設定はしない。終盤に再起動試験。

準備したぞ！という気持ちで当日を迎えました。

## 開始早々、ベンチまでたどり着けない

10時、競技開始。ポータルから CloudFormation のテンプレートを落として、環境を作ります。

ロールバックしました。

EC2 のインスタンスが容量不足だそうです。いきなりかよ、と思いつつ、まあこれは自分のせいじゃないので、焦らず削除して作り直し。今度はちゃんと4台立ちました。

で、SSH がつながらない。

そんなことをやっていたら、最初のベンチが取れたのは 10:28。開始から30分溶けました。**4,253 点**。

練習では環境を建てるところは Terraform が済ませてくれていたので、ここに時間がかかることを見込んでいなかった。完全に自分の甘さでした。

## いざ本番

気を取り直して、まず当日マニュアルを読みます。

今年の問題は ISUREAL。BeReal 風の SNS です。サーバーが4台で、asia に2台、europe と america に1台ずつ。地域間の遅延と帯域制限がルーターで再現されていて、DB は asia の1台を全地域で共有。DB は asia から動かせません。欧米のユーザーは配点が 1.5 倍。

読みながら気になったのは2つでした。

1つは、**遠いリージョンにいるユーザー**。欧米のアプリは SQL を1本投げるたびに asia の DB まで往復する。DB を動かせない以上、遠いリージョンから asia の DB に来る頻度をどう下げるか、という方向のチューニングになりそう。

もう1つは、**画像がめちゃくちゃ多い**。投稿も RealMoji もプロフィールも画像で、これをなんとかしないといけない。

練習どおりに計測を仕込んで、索引を足して **8,297**。倍になりました。この時点で「お、いけるじゃん」という気持ちになります。

ちなみにこの頃、開始して早々に数十万点を叩き出している人がいました。あ、これ今回は無理だな、と分かりました。分かってからは自分のペースで行けたので、むしろよかったです。

で、遠いリージョンの件。リクエストが来たら、とりあえず一回 asia のアプリに飛ばしちゃって、DB の隣で処理して返す。そうすれば往復は1回で済むはず。

やってみました。

CPU が張り付きました。asia1 のアプリが。

じゃあ CPU を減らそう、ということで pprof を見ると、画像の JPEG デコードと署名計算が CPU の大半を食っている。そこを削る。上がる。

すると今度は、**CPU が速くなった分だけリクエストが増えて、DB が張り付く。**

DB の待ちを分解して、ロックの持ち方を変えて、画像の格納方式を変えて、検索の SQL を作り直す。上がる。

するとまた asia1 の CPU が張り付きます。

これを、くるくるくるくる、ずっと繰り返していました。

![スコアの推移](/images/2026-10-31-isucon-2026-isureal/score-timeline.png)

どこかを速くすると次が詰まる。詰まったところを見に行くと、さっきまで見えなかったものが見える。これが全然飽きなくて、めちゃくちゃ面白かったです。

## 当日の体制

- **手元のメインセッション**: サーバーに入る、デプロイする、ベンチを回す、記録する
- **実装ワーカー**: 施策を1つずつコードにして、テストを通して返す
- **クラウドセッション（Opus と Fable）**: 現状分析と、施策を考える係

手元だとトークンの上限が気になるので、たまたまもらっていた $250 分のクレジットを使って、重い分析はクラウド側に投げていました。

特に DB まわりが怪しいことが多かったので、メインセッションが psql で実際の DB の状態（遅いクエリ、ロック待ち、実行計画）を取ってきて、それをクラウドの Fable に投げる、という動きが多かったです。

自分は、ダッシュボードを見て、気になったところをクラウドセッションに聞いて、出てきた施策の中から筋が良さそうなものを選んで、反映してもらう。

おかげで、今何をやっているのかに置いていかれずに改善を進められた感覚があります。これは地味に嬉しかった。

## 一気にスコアが上がった施策

細かい施策は、たぶんみんな同じようなことをやっていると思うので、一気に上がったものだけ。

**索引を足す（4,534 → 8,297）**

画像と友達関係の索引を3本。pg_stat_statements で画像取得のクエリが平均 509ms だったのが 24ms に。定番ですが、定番なだけありました。

**DB 接続を使い回す、画像をディスクから返す（8,297 → 13,220）**

リクエストのたびに接続を張り直していたのをやめて、画像本体は各アプリのディスクにキャッシュして返す。有効性の確認だけ DB に1回。

**書き込みだけを asia のアプリに飛ばす（19,867 → 23,553）**

全部飛ばすと asia1 が詰まったので、POST / PUT / DELETE だけ飛ばして、読み取りと画像は各地域で返す。

実はここで、「遠いリージョンが遅い」の正体が分かりました。往復そのものじゃなくて、**往復しながらロックを握り続けていた**んです。ロックを握っている側のトランザクションが、asia だと 146ms で閉じるのに、欧米だと 600ms 開きっぱなし。書き込みを DB の近くに寄せたら、ロック待ちが観測された時間が 36 秒から 13 秒に減りました。

**JPEG はヘッダだけ読む、署名を使い回す（27,722 → 36,890）**

この日いちばん伸びた一手です。投稿画像の寸法チェックで毎回フルデコードしていたのをヘッダだけに。画像 URL の署名は有効期限を5秒単位で丸めて再利用。asia1 のアプリ CPU の半分がこの2つだったので、削ったら一気に上がりました。

**画像の格納方式を変える、セッションに索引（36,890 → 44,034）**

画像の列を TOAST の STORAGE EXTERNAL にして、INSERT のたびに再圧縮していたのをやめる。あとセッションのトークンに索引。

**検索を pg_trgm で作り直す（43,158 → 50,972）**

ユーザー検索が毎回 5,000 行を舐めていたので、pg_trgm と名前順の索引で 51 件で打ち切るように。DB の処理時間が 573 秒から 290 秒に。

## 残り2時間で、何も思いつかなくなった

16時くらいでした。

やれることは一通りやって、ダッシュボードを見ても「ここだ」というものがない。クラウドセッションに聞いても、出てくる案の見込みが小さい。

ここで一度、何を考えてきたかを振り返ってもらいました。そのときのメモが、この記事の元になっています。

振り返っていて気づいたのが、後半ずっと「europe と america からのアクセスを、いかに asia の DB につながせないか」を考えていたんですよね。書き込みだけ飛ばす、接続数を絞る、欧米にキャッシュを置く。

で、思いついたのが、**思い切って europe と america に DB を建てちゃう**という案。読み取りレプリカを置いて、読み取りは地域内で完結させる。

ただ、書き込み後の読み取り整合性をどう守るかとか、初期同期で 16GB 送れるのかとか、壁がいくつもある。残り2時間だと、ちょっと時間が足りなさそうでした。

## じゃあ、狙いを変えよう

これ以上スコアを伸ばすのが無理そうなら、どうせなら別のものを獲りにいこう、と思いました。

リーダーボードを見ると、特定の点数ぴったりを狙う特別賞があって、ちょうど自分のスコアがその点数とだいぶ近い。これ、今回の自分の条件に合ってるんじゃない？

というわけで、最後の1時間半は、スコアを上げるチューニングじゃなくて、**スコアをその点数に寄せるチューニング**をしていました。asia の2台への振り分け比率をつまみにして、点を上げたり下げたり。

結果、寄りませんでした。

いちばん近づいたのが 17:00 の 55,605 点。あと 29 点。

そこからも上げたり下げたりしているうちに 18:00 になり、最後の走行が 63,243 点で終了。最終スコアは「最後に回したベンチの点数」なので、結果的にベストに近い点で終われました。

・・・いや、あと 29 点のところで止めとけばよかったのでは？

と、ちょっと思っています。
