## はじめに

船長（せんちょう）と申します。

2年ぶりに開催された ISUCON 2026 に、1人チームで出てきました。

正確には1人ではなくて、手はほぼ全部 AI エージェント（Claude Code と Codex）です。自分はコマンドを打たない。ダッシュボードと看板を見て、次にやることを選んで、一言理由を言う。事前にそう決めて臨みました。

出た理由は、いいスコアを出したかったというのもあるんですが、それ以上に**後日談が欲しかった**んですよね。

バックエンドの性能改善だけに集中できるコンテストって珍しい。同じ問題に強いエンジニアがどう取り組んだのか、自分が詰まったところをみんなはどう乗り越えたのか。それを知るには、まず自分がどこで何を考えていたかを残しておかないと比べられない。

なので、この記事は「何を見て、何を考えて、何をしたか」の記録です。施策の正解集ではありません。

最終スコアと順位、他チームの施策との答え合わせは、結果発表のあとに追記します。
:::

## 事前にやってきたこと

半年くらい前から、自分の仕事の文脈をまるごと AI エージェントに渡すための[バーチャルモノレポ](https://zenn.dev/paraponera/articles/2026-09-09-virtual-monorepo-ai-agent)を育てています。ISUCON もその中の1コンテキストとして準備しました。

やったのは大きく3つです。

**1. 過去問を3回、実環境で解いた**

10月上旬に ISUCON9 予選と ISUCON10 予選、本番の1週間前に private-isu。AWS に競技相当の構成を建てて、AI に計測と実装をやらせ、自分は仮説を立てて答え合わせをする、という進め方です。

ここで食らった失敗がそのまま当日の型になりました。自動更新がスコアをぶらす。設定を一括で変えると何が効いたか分からなくなる。ヒット率を確かめずにキャッシュを入れても効かない。テンプレートを共通化したら /login の出力が変わってベンチが落ちる。

**2. 計測して見る道具を作った**

ベンチの前後でアクセスログ・slow query・CPU・pprof を採って、マシン全体 → API 別 → SQL 別 → 関数別の順に見られるダッシュボード。それと、分析役の AI が「根拠の数字つきで候補カードを積む」看板。自分はカードを見て選ぶだけ、という分業です。

遭遇した改善パターンは1枚ずつ教材にして、「自分で思いつけたか」を記録するようにしました。演習の時点では、はい 7 / いいえ 48。ほとんど思いつけてないです。

**3. 当日の手順と守るものを決めた**

「つなぐ → 守る（Git化・退避）→ 素の基準 → OS が勝手に動かない状態 → 計測を仕込む → 施策」という初動の順番。終盤の再起動試験。それと、耐久性を落とす設定変更はしない、変更は1つずつ戻せる形で、というルールです。

## 問題を見て、最初に気になったこと

今年の問題は ISUREAL。BeReal 風の SNS で、サーバーが4台。asia に2台、europe と america に1台ずつあって、地域間の遅延と帯域制限がルーターで再現されています。DB は asia2 の PostgreSQL 16 を全地域で共有。欧米のユーザーは配点が 1.5 倍。

マニュアルを読みながら最初に引っかかったのは2つでした。

1つは、**遠いリージョンにいるユーザー**。欧米のアプリは SQL を1本投げるたびに asia の DB まで 100ms の往復を払う。これは何か手を打たないとまずい。読み終わる前から「europe と america の DB 接続を減らせないか」と口にしていました。

もう1つは、**画像がめちゃくちゃ多い**こと。投稿も RealMoji もプロフィールも画像で、初期データだけで 180 万枚・14GB が DB の中に入っている。

結果的に、この日の施策はほとんどこの2本の線の上に乗りました。

## 当日の歩み

![スコアの推移](/images/2026-10-31-isucon-2026-isureal/score-timeline.png)

46 回ベンチを回しました。山で区切ると5つです。

### 1. 立ち上がりで30分溶かして、まず計測と索引（10:00〜11:00）

CloudFormation が容量不足でロールバック、作り直したら今度は SSH が通らない。Instance Connect から鍵を足して、素のベンチが取れたのが 10:28。**4,253 点**。

ベンチの出力を見ると europe の投稿期間が開けずにタイムアウトしていて、グランプリの欄が asia 17 人・europe 0 人・america 2 人。top では asia2 の postgres が CPU を使い切っていて、欧米の2台はほぼ寝ている。

練習どおりに計測を仕込んで、索引を3本足して **8,297**。ここで pg_stat_statements の上位に users の表ロックと行ロックが並んでいるのが見えました。

### 2. 「遠い」はロックの問題だった（11:00〜12:40）

欧米のリクエストを nginx から asia1 のアプリへ全部転送してみる。往復 100ms が 1ms になるはず。

下がりました。asia1 の CPU が先に張り付いた。戻します。

ここで一度立ち止まって、律速の分析を「採点 → 各台の資源 → API → DB → アプリ CPU → 地域間往復」の順でやり直してもらいました。出てきたのが、DB 時間の半分がユーザー行のロック待ち。しかもロックを握っている側のトランザクションが、asia だと 146ms なのに europe と america だと 600ms 開いたまま。

**遠いのは往復そのものじゃなくて、往復しながらロックを握り続けることだった。**

なので書き込みだけを asia1 へ転送して、読み取り・画像・SSE は各地域で返す形に。待ちが観測された時間が 36 秒から 13 秒に減って **23,553**。そのまま asia2 にもアプリを置いて振り分けて **27,722**。

途中、export の画像取得が N+1 でベンチが FAIL（0点）。「export は配点 20 だから、戻すだけじゃなくて速くする」と決めて作り直しました。

### 3. CPU の中身を見たら、JPEG と署名だった（12:40〜13:20）

ここで pprof を見ると、asia1 のアプリ CPU の半分が投稿画像の JPEG デコード、4分の1が画像 URL の署名計算。

投稿の寸法チェックをヘッダだけ読む形にして、署名を5秒単位で使い回す。これで **36,890**。この日いちばん伸びた一手です。

勢いで「A〜F 全部入れましょう」と提案が来たんですが、ここは止めました。**DB が CPU で詰まってるのか、どのクエリが重いのかを先に見る。** 画像列を TOAST の STORAGE EXTERNAL にして再圧縮をやめ、セッションの索引を足して **44,034**。

### 4. DB の待ちを分解する（13:20〜15:00）

DB の稼働を分けると、CPU 24%・データ読み 24%・テーブル拡張ロック 17%・WAL 15%。画像の INSERT が月別のパーティション1枚に集中して、拡張ロックを取り合っている。

検索 SQL を pg_trgm で作り直して **50,972**。ただしその前に入れた「SQL で絞る」版は旧実装より遅くて、一回やり直しています。

export は DB じゃなくてディスク読みが律速だと分かったので、初期画像をアプリ側のディスクに事前キャッシュする案が出る。9GB・62 万枚。「終わらない」と一度捨てました。でも他の手が細くなってきて、結局 asia1 で 27 分かけて実行。DB 時間は 3 割減ったのに、点は下がる。

asia2 にもキャッシュを入れて振り分けを 2:1 にしたら **58,241**。何が効いたのかは、正直まだ分けられていません。

### 5. 終盤、一つずつ、そして狙いを変える（15:00〜）

ここからは一つ入れたら測る、の繰り返しです。

署名の期限を 60 秒単位にして 58,704。新規画像のパーティションを HASH で 8 分割して **59,264**。15:25 に 4 台まとめて再起動試験、10 秒で復帰、そのまま 57,009 で PASS。

ユーザー行のロックをペア単位の advisory lock に置き換える案は、区切り文字に NUL を使って一度 FAIL。直して 55,705。同じコードを計測スクリプトなしで回したら **63,402**。計測の負荷でこんなに動くのか、とここで初めて気づきました。

で、ここで狙いを変えました。リーダーボードを見ると「ココロザシ賞」の 55,634 点ぴったりを 6 点差で狙っているチームがいる。最高点をさらに伸ばす見込みも聞いた上で、こっちを獲りにいくことにしました。振り分け比率をつまみにして、点を下げる方向に調整しています。

## やったことをざっくり

76 枚カードを切って、残ったのは大きく6テーマです。

| テーマ | やったこと |
| --- | --- |
| 索引と接続 | 画像・友達関係・セッションの索引。DB 接続の再利用。欧米だけ接続上限を 10 に。shared_buffers 1GB |
| 地域の配置 | 書き込みだけ asia1 へ転送。asia2 にもアプリを置いて振り分け（5:1 → 2:1 → 3:1） |
| ロック | ユーザー行ロックのまとめ取得、トランザクションを短く、友達申請の往復 6→3、最後はペア単位の advisory lock |
| 画像 | ディスクキャッシュ、X-Accel-Redirect、STORAGE EXTERNAL、JPEG はヘッダだけ、初期画像の事前キャッシュ、パーティション 8 分割 |
| 署名 | HMAC の計算を減らす。期限を 5 秒 → 60 秒単位で丸めて再利用 |
| PostgreSQL の設定 | WAL・checkpoint・bgwriter。ベンチ直前に CHECKPOINT を済ませる |

やめたもの・入れなかったものも書いておきます。欧米 API の全転送（asia1 が詰まる）。投稿処理を DB 関数に集約（往復はもう 1ms なので効かず）。欧米に画像キャッシュ（同じ画像が 2〜3% しか再来しない）。欧米に読み取りレプリカ（初期同期 16GB と read-after-write が壁。次回向け）。

## 学んだこと

### 事前の理解で通用したもの

- 初動の順番はそのまま使えた。SSH で 30 分溶かしても、そこから先は型どおりに戻れた
- 索引と N+1。最初の2倍も、唯一の FAIL も、結局これ
- 「分散させると次が見えてくる」。asia2 にアプリを足したら律速が DB に移った。ISUCON10 で体験したやつ
- 変更は1つずつ、戻せる形で。終盤に「3:2 も試そう」と走り出したワーカーを止めたのは、この型があったから
- ヒット率を先に確かめる。ISUCON9 で効かなかったキャッシュの教訓が、今回は画像キャッシュを保留する判断になった
- 再起動試験は終盤前に1回。公開知見で失格原因の1位

### 今日初めて出会ったもの

- **地域間の遅延は、往復の数じゃなくてロックの保持時間に効く。** 往復を減らすより、書き込みを DB の近くに寄せる
- PostgreSQL の引き出し。TOAST の格納方式、パーティションへの同時 INSERT の拡張ロック、チェックポイント直撃、prepared statement の汎用プランで索引が外れる、pg_trgm、advisory lock。MySQL で練習してきたので、ここは全部その場で覚えました
- 署名 URL の HMAC がアプリ CPU の過半を占める、という構造
- 欧米ユーザーの「人数」が得点を決めていて、しかもベンチが性能に応じて人数を増やしてくる
- 計測スクリプトの有無で数千点動く

### 予想とずれたもの

- 全転送で asia1 が先に詰まった
- 検索を SQL で絞ったら逆に遅かった
- DB 関数は効かなかった
- 事前キャッシュで DB 時間は減ったのに点は下がった
- 「同じ構成でも 2,000 点ぶれる」は、根拠が1組しかなかった

### AI と組んでやってみて

判断役に徹してコマンドを打たない、という分担は回りました。ただ、回ったのは「選ぶ」ところまでで、看板に積まれたカードの根拠の数字を見て選ぶ以上のことは、まだあまりできていません。

一方で、一括投入を止めて「先に内訳を見せて」と言った場面が2回あって、どちらも次の一手が変わりました。事前に 50 枚近い「いいえ」を積んでおいたから、ここだけは自分で判断できた気がします。

判断の記録は時刻がずれる、というのも学びです。AI が時計を見ずに書く。run の ID と突き合わせないと振り返りに使えない。
