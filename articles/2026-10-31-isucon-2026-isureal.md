## はじめに

船長（せんちょう）と申します。

2年ぶりに開催された [ISUCON 2026](https://isucon.net/archives/59917350.html) に、初めて出てきました。

実務でパフォーマンスチューニングをやった経験はほぼないです。前職で Datadog を眺めて、エラーが起きたらログを追って解消する、くらい。インフラとバックエンドも、まあちょっと触ったことはあるよ、という程度でした。

それでも出ようと思ったのは、バックエンドの改善点をひたすら探して直す、というのが単純にめっちゃ面白そうだったからです。

それと、同じ問題を解いた強い人たちが、終わったあとに体験談を出してくれるじゃないですか。それを全部読める。これがすごくいいなと思いました。

自分が詰まったところを、みんなはどうやって越えていったのか。それを知るには、まず自分がどこで何を考えていたかを残しておかないといけない。

なので、この記事はその記録です。

今回の目標は、スコアそのものより、終わったあとに参加者のブログを読んで学ぶこと。だから、自分が律速になるのは分かった上で、AI に教えてもらいながらやる、と最初から決めていました。

結果から書いておくと、最終スコアは **63,243 点**（順位は追記）でした。想定より結構うまく頑張れたんじゃないかな、と思っています。

## 準備したこと

1人チームです。コードを書くのは AI エージェント。

ただ、AI に「とりあえず改善して」と任せるだけだと、何が起きているのか何も分からないんですよね。

だから、自分が分かるように、**一次情報の集め方と表示の仕方**を、当日までに間に合う範囲で準備することにしました。

やったのは3つです。

**過去問を3回、AWS に環境を建てて解いた。**

最初の2回（ISUCON9 と ISUCON10 の予選）は、AI に解いてもらいました。答えも全部見ながら、なるべく高い点数になるように。そこで得た知見を、改善パターンとしてまとめてもらいました。

3回目の private-isu は、自分で。育ってきたダッシュボードとパターン集を見ながら、本番のつもりで一緒に解いてみました。

**ベンチの前後で一次情報を採って、見られるようにした。**

アクセスログ、slow query、各プロセスの CPU、pprof。これをベンチのたびに採って、「どの API が遅いか」「どのプロセスが CPU を食っているか」「どのクエリが重いか」「どの関数に時間がかかっているか」を、前回との差分つきで見られるダッシュボードにしました。

![API ごとの回数・合計時間・p99・転送量。遅いものに「重」「注意」の札がつく](/images/2026-10-31-isucon-2026-isureal/dashboard-api-list.png)
*ベンチが終わると、API 一覧がこう出ます。この回は通知の SSE が 71% を占めていますが、接続しっぱなしなので遅さとは別です*

![判断材料。遅いクエリ、プロセスごとの CPU、関数ごとの時間、台ごとの CPU を一画面に](/images/2026-10-31-isucon-2026-isureal/dashboard-judgement.png)
*その下に「判断材料」。遅いクエリ、どの台のどのプロセスが CPU を食っているか、pprof で関数ごとの時間、台ごとの CPU。これを見て「次はここかな」を決めていました*

**当日の手順と、守るものを決めた。**

まず当日マニュアルを読む。これが一番大事だと、事前に読んだ体験談のほとんどに書いてあったので。そのあとは、つなぐ → 退避 → 素の基準 → 計測を仕込む → 施策、の順番で進める。変更は1つずつ戻せる形で入れる。耐久性を落とす設定はしない。終盤に再起動試験をする。ここまで決めておきました。

準備したぞ！という気持ちで当日を迎えました。

## 開始早々、ベンチまでたどり着けない

10時、競技開始。ポータルから CloudFormation のテンプレートを落として、環境を作ります。

が、ロールバックされました。

EC2 のインスタンスが容量不足だそうです。いきなりかよ、と思いつつ、まあこれは自分のせいじゃないので、焦らず削除して作り直し。今度はちゃんと4台立ちました。

で、今度は SSH がつながらない。

そんなことをやっていたら、最初のベンチが取れたのは 10:28。開始から30分溶けました。**4,253 点**。

練習では環境を建てるところは Terraform が済ませてくれていたので、ここに時間がかかることを見込んでいなかったんですよね。完全に自分の甘さでした。

## いざ本番

気を取り直して、まず当日マニュアルを読みます。

今年の問題は ISUREAL。BeReal 風の SNS です。

@[youtube](dBONTxQB-w4)

サーバーが4台で、asia に2台、europe と america に1台ずつ。地域間の遅延と帯域制限がルーターで再現されていて、DB は asia の1台を全地域で共有。DB は asia から動かせません。欧米のユーザーは配点が 1.5 倍。

読みながら気になったのは2つでした。

1つは、**遠いリージョンにいるユーザー**。欧米のアプリは SQL を1本投げるたびに asia の DB まで往復する。DB を動かせない以上、遠いリージョンから asia の DB に来る頻度をどう下げるか、という方向のチューニングになりそうです。

もう1つは、**画像がめちゃくちゃ多い**。投稿も RealMoji もプロフィールも画像で、これをなんとかしないといけない。

練習どおりに計測を仕込んで、索引を足して **8,297**。倍になりました。この時点で「お、いけるじゃん」という気持ちになります。

ちなみにこの頃、開始して早々に数十万点を叩き出している人がいました。あ、これ今回は無理だな、と分かりました。分かってからは自分のペースで行けたので、むしろよかったです。

で、遠いリージョンの件。リクエストが来たら、とりあえず一回 asia のアプリに飛ばしちゃって、DB の隣で処理して返す。そうすれば往復は1回で済むはず。

やってみました。

すると、asia1 のアプリの CPU が張り付きました。

じゃあ CPU を減らそう、と pprof を見ると、画像の JPEG デコードと署名計算が CPU の大半を食っている。そこを削ると、スコアが上がる。

すると今度は、**CPU が速くなった分だけリクエストが増えて、DB が張り付く。**

DB の待ちを分解して、ロックの持ち方を変えて、画像の格納方式を変えて、検索の SQL を作り直す。また上がる。

すると、またしても asia1 の CPU が張り付きます。

これを、くるくるくるくる、ずっと繰り返していました。

![スコアの推移](/images/2026-10-31-isucon-2026-isureal/score-timeline.png)

どこかを速くすると、次のボトルネックが出てくる。そこを見に行くと、さっきまで見えなかったものが見える。これが全然飽きなくて、めちゃくちゃ面白かったです。

## 当日の体制

- **手元のメインセッション**: サーバーに入る、デプロイする、ベンチを回す、記録する
- **実装ワーカー**: 施策を1つずつコードにして、テストを通して返す
- **クラウドセッション（Opus と Fable）**: 現状分析と、施策を考える係

お金の話もしておくと、手元は Claude の月 100 ドルのプラン。クラウドセッションは、たまたまもらっていたクレジットから 120 ドルくらい使いました。手元だとトークンの上限が気になるので、重い分析はクラウド側に投げる、という使い分けです。

それと、事前に作っていた private の[バーチャルモノレポ](https://zenn.dev/paraponera/articles/2026-09-09-virtual-monorepo-ai-agent)に、ISUCON の目標・現在地・ルール・練習で得たパターンを置いてありました。なので、どのセッションも「今どういう状況で、何を守るか」を自分で読みに行けます。毎回説明しなくて済んだので、これはかなり助かりました。

特に DB まわりが怪しいことが多かったので、自分が psql を手で叩いて、遅いクエリ・ロック待ち・実行計画をクラウドの Fable にコピペする、という人力プロキシをよくやっていました。

あとは、ダッシュボードを見て、気になったところをクラウドセッションに聞いて、出てきた施策の中から効きそうなものを選んで、反映してもらう。

おかげで、今何をやっているのかに置いていかれずに改善を進められた感覚があります。ここは普通に嬉しかったです。

## 一気にスコアが上がった施策

細かい施策は、たぶんみんな同じようなことをやっていると思うので、一気に上がったものだけ。

**索引を足す（4,534 → 8,297）**

画像と友達関係の索引を3本。pg_stat_statements で、画像取得のクエリが平均 509ms だったのが 24ms になりました。定番ですが、定番なだけありました。

**DB 接続を使い回す、画像をディスクから返す（8,297 → 13,220）**

リクエストのたびに接続を張り直していたのをやめて、画像本体は各アプリのディスクにキャッシュして返す。DB には有効性の確認で1回だけ行く。

**書き込みだけを asia のアプリに飛ばす（19,867 → 23,553）**

全部飛ばすと asia1 が詰まったので、POST / PUT / DELETE だけ飛ばして、読み取りと画像は各地域で返すようにしました。

実はここで、「遠いリージョンが遅い」の正体が分かりました。往復そのものじゃなくて、**往復しながらロックを握り続けていた**んです。ロックを握っている側のトランザクションが、asia だと 146ms で閉じるのに、欧米だと 600ms 開きっぱなし。書き込みを DB の近くに寄せたら、ロック待ちが観測された時間が 36 秒から 13 秒に減りました。

**JPEG はヘッダだけ読む、署名を使い回す（27,722 → 36,890）**

この日いちばん伸びた一手です。投稿画像の寸法チェックで毎回フルデコードしていたのを、ヘッダだけ読むように。画像 URL の署名は、有効期限を5秒単位で丸めて再利用。asia1 のアプリ CPU の半分がこの2つだったので、削ったら一気に上がりました。

**画像の格納方式を変える、セッションに索引（36,890 → 44,034）**

画像の列を TOAST の STORAGE EXTERNAL にして、INSERT のたびに再圧縮していたのをやめる。あとセッションのトークンに索引。

**検索を pg_trgm で作り直す（43,158 → 50,972）**

ユーザー検索が毎回 5,000 行を舐めていたので、pg_trgm と名前順の索引で 51 件で打ち切るように。DB の処理時間が 573 秒から 290 秒になりました。

## 残り2時間で、何も思いつかなくなった

16時くらいでした。

やれることは一通りやって、ダッシュボードを見ても「ここだ」というものがない。クラウドセッションに聞いても、出てくる案の見込みが小さい。

ここで一度、今日ここまで何を考えてきたかを振り返ってもらいました。そのときのメモが、この記事の元になっています。

振り返っていて気づいたんですが、後半ずっと「europe と america からのアクセスを、いかに asia の DB につながせないか」を考えていたんですよね。書き込みだけ飛ばす、接続数を絞る、欧米にキャッシュを置く。

で、思いついたのが、**思い切って europe と america に DB を建てちゃう**という案。読み取りレプリカを置いて、読み取りは地域内で完結させる。

ただ、書き込み後の読み取り整合性をどう守るかとか、初期同期で 16GB 送れるのかとか、考えないといけないことがいくつもある。残り2時間だと、ちょっと足りなさそうでした。

ここは悔しかったところです。欧米のユーザー数が、最後まで全然増えなかったんですよね。asia は 17 人から 379 人まで伸びたのに、欧米は数十人止まり。配点 1.5 倍のところが伸びていない。

思いついたときにはもう遅くて、試していたら変わっていたのかなと思いつつ、終わったあとに参加者の声を見ていたら、たぶんそれはそれで失敗していただろうな、とも思いました。もっといろんなやり方があったんだな、と。

## じゃあ、狙いを変えよう

これ以上スコアを伸ばすのが無理そうなら、どうせなら別のものを獲りにいこう、と思いました。

リーダーボードを見ると、[ココロザシ](https://kokorozashi-japan.co.jp/)さん提供のココロザシ賞という、55,634 点ぴったりを狙う特別賞があります。ちょうど自分のスコアがその点数とだいぶ近い。これ、今回の自分の条件に合ってるんじゃない？

というわけで、最後の1時間半は、スコアを上げるチューニングじゃなくて、**スコアをその点数に寄せるチューニング**をしていました。asia の2台への振り分け比率をつまみにして、点を上げたり下げたり。

結果、寄りませんでした。

いちばん近づいたのが 17:00 の 55,605 点。あと 29 点。

そこからも上げたり下げたりしているうちに 18:00 になり、最後の走行が 63,243 点で終了。最終スコアは「最後に回したベンチの点数」なので、結果的にベストに近い点で終われました。

・・・いや、あと 29 点のところで止めとけばよかったのでは？

と、ちょっと思っています。

## 振り返って

残り2時間でやれることがなくなって、うーん、となっていたので、限界といえば限界でした。でも、頑張ったかな、とも思います。これ以上の出来は、現時点の自分では無理だったと思います。

最初に書いたとおり、今回の目標は終わったあとに参加者のブログを読んで学ぶことで、自分が律速になるのは分かった上で、教えてもらいながらやるつもりでした。

でも、やっぱりスコアが上がるのが楽しくて。気づいたら、改善を回すことばかりやっていました。結局、自分で把握できていたのは、**今どこが律速になっているか、くらいだった**なと思います。

それでも、直すたびに次のボトルネックが出てきて、見に行くと見えなかったものが見える、というのを1日中やれたのは、めちゃくちゃ面白かった。初参加の体験記としては、これでいい流れだったんじゃないかと思っています。

あと、作問のすごさを思い知りました。

参加者のほとんどが AI を使っているはずなのに、ちゃんと点数がばらけている。索引を足せば終わり、ではなくて、地域のロック、画像、署名と、見に行かないと分からない層がいくつも重なっている。この問題を作る力量に感動しました。

そして何より、**人間側の能力次第で、改善の余地がまだめちゃくちゃある**ことが分かって、超嬉しいし、悔しい。ワクワクしています。

## おわりに

他の人がこの問題をどう見たかが知りたいです。遠いリージョンのユーザーをどう扱ったのか。画像をどこに置いたのか。DB を欧米に建てた人はいたのか。画像 URL の署名計算が最後まで CPU に残ったんですが、あれはどうやったら削れたんだろう。

答え合わせができたら、またここに書きます。

実務では触れないところを1日中これだけ考えられる環境、やっぱり貴重でした。

これからも精進します！
